# Operations monitoring contract

Accepted design for OPS-001, 19 October 2026. Inventory (OPS-002), credential management
(OPS-003), durable ingestion (OPS-004) and health/history (OPS-005) are implemented in [live OpenAPI](openapi.yaml),
disabled by default behind separate source rollout flags. Historical production
enablement of inventory/credentials is recorded in the handoff; this health change
applies no production setting. The [planned OpenAPI](operations-planned.openapi.yaml)
retains schema fixtures. Incident and probe contracts below remain future requirements;
incident routes will be specified before OPS-006 implementation.

## Baseline and placement

Reconciled against `87256b7` plus the update-security changes in PR #15. Products are global
commercial catalog entries; organizations and memberships are in `auth`; there is no application
or environment inventory. `SecurityCenter` is account/device oriented. Client events pass through
ADR-027 and `PgTelemetrySink` buffers ordinary telemetry, so neither is a durable backend collector.
`recordSecurity` writes synchronously but lacks integration attribution, deduplication and quotas.
`/healthz` currently establishes process liveness only. Existing organization permissions do not
grant monitoring authority. Business Admin provisioning and shared Rokela PDF subscriptions remain
independent of this new domain.

Introduce `packages/operations` with dependencies only on `audit`, `crypto`, `shared-types` and
`telemetry` (content detectors). Inject actor authorization and optional Product validation at the
composition boundary; do not import auth/licensing into this package. Add the package to the boundary
checker and allow `platform-api` to compose it. Place HTTP schemas/routes and PostgreSQL adapters in
`platform-api`. Do not add integration secrets, service calls or monitoring authority to `sdk-core`.

## Ownership and permissions

Every application belongs to exactly one organization. Its immutable code is unique within that
organization, including archived rows. Environments have immutable codes unique within an application;
components have immutable codes unique within an environment. IDs are generated by Warrior, not by
callers: `opa_`, `ope_` and `opm_` plus 24 lowercase hex characters for application, environment and component; existing organization/user/Product IDs retain their current formats. Code syntax is `[a-z][a-z0-9-]{1,47}`. Labels use the same content-free syntax; no arbitrary
names, descriptions, customer identifiers or URLs are accepted as inventory labels. Display friendly
names locally if needed. Applications have an accountable `owner_user_id` who must be an active member
of the same organization, a `low|medium|high|critical` criticality and optional active catalog Product ID.
A Product mapping conveys no entitlement, membership or monitoring credential. Dependencies reference
components within the same organization; reject cycles and cross-tenant references.

Inventory grants shipped in OPS-002; the remaining grants ship with their tasks:

| Permission               | Ordinary member | Organization admin/owner | Authority                                                           |
| ------------------------ | --------------- | ------------------------ | ------------------------------------------------------------------- |
| `ops:read`               | No              | Yes                      | Inventory, event/health history and incidents in own organization   |
| `ops:manage_inventory`   | No              | Yes                      | Create/update/archive inventory with reason                         |
| `ops:manage_credentials` | No              | Yes                      | Issue/rotate/revoke credentials with fresh MFA and reason (OPS-003) |
| `ops:manage_rules`       | No              | Yes                      | Rules, maintenance windows and verified destinations (OPS-006)      |
| `ops:manage_incidents`   | No              | Yes                      | Assign, acknowledge and resolve incidents with reason (OPS-006)     |

No permission implies `license:*`, membership changes, platform-operator status or remediation authority.
Do not silently grant monitoring reads to existing ordinary organization members. Operators need the
same membership/permission checks; no new cross-tenant operator bypass is introduced. A nonmember or
wrong ancestor/resource returns 404; an authenticated member lacking the permission returns 403. Check
membership before freeze/state errors. Authentication failure returns 401 without object existence hints.
Credential issue, rotation and revocation require `mfa_code` (a current six-digit authenticator code). After membership/permission checks, call existing `AuthService.stepUp` with the live session/user; recovery codes and client-supplied MFA flags do not qualify. The factor is consumed/audited in its auth transaction before the operations mutation; a later mutation failure does not restore the code. Never persist/reflect/log the code.

Inventory mutations require `reason` and append audit through the same operations transaction. Reasons
are bounded reviewed codes (e.g. `initial_setup`, `owner_transfer`, `maintenance`, `retirement`), not free
text. Updates include `expected_version`; mismatches return 409 with no partial write/audit. Parents are
locked organization → application → environment → component, then credential/counter/event. Freeze blocks management
writes and credential issuance/rotation; it preserves authorized reads, ingestion and emergency revocation.
Ingestion is observational only. Implement revocation as the explicit freeze exception and audit it.

Lifecycle: `active → disabled → active`, or either → `archived` (terminal). DELETE is soft archive, audited,
and accepts expected version/reason. No code/ID reuse. Archived/disabled ancestors block new credentials,
events and rules even if descendants are active. Disable temporarily suspends use of descendant credentials;
reactivation permits only still-unexpired, unrevoked credentials. Archive permanently blocks use through that
ancestor; it is terminal. Neither lifecycle transition can resurrect revoked credentials. Existing history remains readable until retention
expires. Components have kind `service|database|storage|worker|scanner|desktop|provider`; environments have
kind `development|staging|production`. Dependencies are an inventory graph, never URLs to execute.
Lists use opaque last-ID cursors scoped to the organization/parent, ordered ID ascending, limit 1–100;
invalid/cross-parent cursors return 400. Counts include archived rows; defaults list active and disabled rows.

## Integration credential lifecycle (OPS-003)

Use HTTPS bearer credentials `ops_v1.<credential-id>.<secret>`. The public ID is `opc_` plus 32 lowercase
hex characters; the secret is 32 CSPRNG bytes encoded as 64 lowercase hex characters. Never reuse a license
key, signing key, password or user/operator session. Issue separate credentials for every application,
environment and purpose. Initial purpose is exactly `events:write`, source exactly `backend_report`.
Independent probes and browser reports cannot use it. The authenticated credential row supplies org,
application, environment and source; reject scope fields in the body and any component outside that scope.
Credentials cannot read inventory/history or mutate incidents. Authentication proves attribution, not truth.

Store SHA-256 verification material and public ID, never plaintext. Random 256-bit secrets do not need password
stretching. Compare fixed-length digests with timing-safe comparison; handle unknown IDs with a dummy digest.
Do not log headers, secret-bearing bodies or credential fingerprints. Auth errors are generic. Secrets are
returned once on issue/rotation with `Cache-Control: no-store`; list/read responses contain metadata only.
The issue response is inherently unrecoverable after a lost response: list IDs and rotate/revoke with fresh MFA,
never replay an issue request to retrieve the old secret. Enforce 1–90-day TTL and at most two unrevoked,
unexpired credentials per environment/purpose (including an overlap predecessor).

Rotation locks the environment and predecessor, issues a successor and sets predecessor expiry to the earlier
of its current expiry and now + requested overlap (0–3600 seconds). Never extend an expiry; overlap 0 revokes
immediately. Do not allow a second rotation until the overlap predecessor is expired/revoked. Revocation is
idempotent, audited on the first transition, and immediately rejects new committed ingestion. Ingestion checks
credential/ancestor state under the same transaction locks as rotation/revocation; if revocation wins, ingestion
fails, otherwise the already committed acknowledgement remains valid. A stolen active bearer can submit fresh
false observations until revoked: quotas, strict privacy schemas and provenance labeling limit impact. Durable
IDs deduplicate delivery; they are not proof that an event was honestly produced. No HMAC timestamp/replay
protocol is implied by this bearer design.

## Version 1 events and privacy (OPS-004)

POST `/v1/operations/events` uses only the integration bearer, never account session auth. A request has exactly
`schema: 1` and `events` (1–100). Each event has UUIDv4 `id`, `component_id`, RFC3339 UTC `occurred_at`, `type` and
a strict type-specific `attributes` object. Severity, actor identities, organization/application/environment,
source, receipt time, URLs, free-form message, stack and correlation strings are not accepted. Component IDs are
Warrior-generated opaque references, not filenames/job IDs. UUID event IDs are generated once by the producer
and survive outbox retries. No source request/document identifiers are allowed in version 1.

| Type                          | Exact required attributes                             | Allowed values/bounds                                                             |
| ----------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------- |
| `component.heartbeat`         | `status`                                              | `healthy`, `degraded`, `unavailable`, `unknown`                                   |
| `upload.failed`               | `stage`, `reason`, `duration_ms`, `size_bucket`       | stage `initiate                                                                   | transfer    | finalize`; reason `timeout                         | storage_unavailable      | quota                                 | validation                               | internal`; duration 0–86400000; size `small | medium                         | large | unknown` |
| `conversion.failed`           | `source_type`, `target_type`, `reason`, `duration_ms` | types `pdf                                                                        | image       | office                                             | text                     | other`; reason `timeout               | unsupported                              | worker_unavailable                          | internal`; duration 0–86400000 |
| `scanner.unavailable`         | `reason`, `queue_age_seconds`, `queue_count`          | reason `timeout                                                                   | connection  | worker_unavailable`; age 0–604800; count 0–1000000 |
| `malware.detected`            | `verdict`                                             | `malicious`, `suspicious` (backend assertion, never a platform-confirmed verdict) |
| `email.delivery_failed`       | `provider`, `reason`, `attempts`, `queue_age_seconds` | provider `resend                                                                  | cloudflare  | other`; reason `timeout                            | rejected                 | provider_unavailable                  | exhausted`; attempts 1–100; age 0–604800 |
| `request.submission_received` | `file_count`, `state`                                 | count 0–1000; state `received                                                     | quarantined | ready`                                             |
| `link.abuse_reported`         | `category`, `state`                                   | category `spam                                                                    | malware     | phishing                                           | other`; state `received  | triaged`                              |
| `workspace.role_changed`      | `from_role`, `to_role`, `outcome`                     | roles `none                                                                       | member      | admin                                              | owner`; outcome `allowed | denied`; no affected-person reference |

All numeric attributes are integers. Every object rejects unknown properties. Apply ADR-027 detectors to allowed
non-structural strings as defense in depth; envelope UUIDs, times and opaque component IDs use their strict
structural validators rather than secret/phone heuristics. Do not add these backend types to the browser client
schema. Keep unexpected attribute names out of logs/responses too: map them to a fixed `unknown_attribute` code.
No filenames, recipients, private links, secrets, card/phone/email data, raw bodies or unrestricted stack traces
are stored. Document content encoded as enumerated/numeric observations remains a covert-channel residual risk
from a compromised sender; size/quotas and trusted source labels do not prove honesty.

Server-derived attribution is immutable. `received_at` is server UTC time. New events must occur within the
previous 24 hours and at most 5 minutes in the future. First validate schema, then look up scoped duplicate IDs
before checking occurrence freshness; an exact retry of a previously committed event can succeed during its
retention period. Store canonical hash of validated type/component/time/attributes, not raw request bytes.
JSON key order does not matter; the accepted timestamp string is part of identity (a changed spelling conflicts).
Deduplication key is `(org_id, application_id, environment_id, event_id)` across credential rotation. A reused ID
with different validated content is 409. The same UUID in another scope is independent. Mixed batches are atomic:
any malformed, out-of-scope, conflicting or stale new event rejects the whole batch with no stored values/audit.
Duplicate IDs within one batch: identical entries count once; different entries conflict. Dedup occurs before
quota charge. Identity tombstones retain hash/receipt/attribution for 30 days, matching event retention; no claim
of exactly-once behavior after expiry. Old retries then fail the 24-hour new-event freshness window.

Respond 200 only **after transaction commit**, `{schema:1, accepted:[{id, disposition, received_at}]}` in first-ID
appearance order, `disposition: stored|duplicate`, one entry per unique ID. A batch of duplicates is 200 with no
new quota charges. No 202/in-memory acknowledgement. Commit ambiguity is a retryable outage; the sender retries
unchanged IDs. Operational events do not each create global audit-chain records; committed operations storage is
the evidence. Credential/rule/incident/management state changes remain transactionally audited.

## Budgets, retention and failure semantics

Reject encoded or decoded bodies above 256 KiB, unsupported content encoding, batches above 100 and JSON nesting
above the exact schema depth. Rate limits: per credential 60 requests per sliding 60-second window, environment 10000 new events/day
and 500 MiB stored event bytes, organization 100000 new events/day and 2 GiB stored bytes; UTC calendar day.
Count validated canonical bytes plus a fixed 512-byte row allowance against storage quota. Database counters and
new-event insertion are atomic under org → app → env locks. Duplicates consume request budget, not event/storage
budget. Refuse excess with 429 and `Retry-After`; do not evict evidence to accept a flood. Apply a separate coarse
IP request budget before authentication; never let rejected source input increment commercial quotas. Inventory
caps: 100 applications/org, 20 environments/app, 100 components/env; reject at 409 under parent lock.

Raw operational events/identity rows: 30 days. Hourly aggregates: 90 days, by scoped component/type/outcome only,
with no additional identifiers. Incidents/actions: 365 days; notification metadata: 30 days, encrypted payloads
only while pending, maximum 72 hours. Audit uses its existing independent retention/anchor policy. Retention
workers delete in batches <=1000 with indexed expiry and atomically release storage accounting. Archived inventory
keeps attribution rows/tombstones; deletion of linked Product/owner membership never reparents evidence. Owner
removal must require an explicit audited transfer first. Read APIs distinguish expired evidence from an empty
healthy interval; a data gap cannot be a success signal.

Source outbox: durable local queue capped at 10000 events/10 MiB, at most 24 hours old. Enqueue asynchronously from
business outcomes and never block/roll back business work on monitoring failure. Reserve capacity for failures,
drop oldest low-priority observations first, then refuse additional monitoring events while recording a local
dropped/backlog counter. This is visible degraded monitoring, never an application transaction failure. Send 100
at a time with 10-second transport timeout; exponential full jitter 1–300 seconds. Retry network/408/429/5xx
unchanged; respect bounded `Retry-After`. Quarantine 400/409/422 batches locally and expose a count (no values in
logs); pause delivery on 401/403 until configuration repair. Do not try to obtain an operator session. Collector
DB/commit failure returns 503 with no durable acknowledgement, not a success through the telemetry buffer.

Generic problem responses include stable code/status and optional event index/fixed field path/rule, never
submitted values, request bodies, unknown attribute names, raw zod issues or auth detail. 400 malformed body;
401 invalid credential/session; 403 known member lacking permission/freeze; 404 inaccessible scope/resource;
409 version, identity or lifecycle conflict; 413 oversized; 415 unsupported encoding/media type; 422 new-event
clock window/privacy/schema failure; 429 budget; 503 unavailable. Only rate limit responses carry Retry-After.

## Health, probes and incidents (OPS-005/006)

Keep liveness separate from readiness: readiness checks DB access and configured required dependencies using
fixed internal connections; it must not include secrets or identify tenants publicly. Detailed dependency
statuses require `ops:read`. A component heartbeat is a backend report, not an independent probe. At a configured
60-second heartbeat interval, a report expires after 180 seconds of **receipt time**. Missing/no observation is
`unknown`; late expected observations are `stale`; neither is `healthy`. Explicit unavailable wins until a fresh
healthy report; recovery requires fresh evidence. Persist observations/history and maintenance windows. Warrior
must have an external independent monitor; its own dashboard cannot prove its own availability.

OPS-005 freshness amendment: only heartbeats occurring between receipt minus 120 seconds
and receipt can establish current state. Future and older reports are retained evidence only.
The latest eligible occurrence wins regardless of arrival order. Equal-occurrence ties prefer
unavailable, degraded, unknown, healthy; repeated occurrence cannot refresh TTL. Latest eligible
state commits with the event and survives restarts. Inactive ancestry forces unknown. Each read
reports own state and dependency states; unavailable dependencies propagate unavailable, and
other non-healthy dependencies downgrade otherwise healthy reports to degraded. History counts
backend assertions, with no success inference from empty buckets. See [health rollout and read
protocol](../deploy/operations-health.md) and live OpenAPI for window, truncation and gap semantics.
Maintenance-window configuration and notification suppression remain OPS-006.

Network probes are **disabled in the initial milestone**. Inventory and event fields cannot create a destination.
Future probes require a separate ADR amendment and operator-approved ownership proof on an exact host, HTTPS 443,
GET/HEAD only, no credentials/query/fragment/redirects, all IPv4/IPv6 answers checked for non-public addresses,
DNS pinned per connection with TLS hostname verification, response/time/size/concurrency budgets and an isolated
egress worker. Refuse loopback/private/link-local/metadata, IPv4-mapped IPv6 and DNS-rebinding/redirect bypasses.
Private destinations require a separately approved allow-list and isolated worker, never a broad network-scanning
feature. No URL from an event is executed, including in notifications/runbooks.

Rules are server-owned typed predicates per scoped component/type (no scripts/SQL). Evaluate receipt-time windows
with bounded count/duration thresholds, require at least one positive observation, and distinguish missing data.
Default severity is informational; `malware.detected` is an asserted security warning, not confirmed malware.
Incidents use a unique active `(org, app, env, component, rule)` key, open → acknowledged → resolved; ack/resolve
needs permission/reason, and assignment must be to an active member of that organization. Repeated evidence
updates the existing incident without another open notification. A new qualifying observation after resolution
opens a new incident. Resolution never edits source evidence or clears a license/device restriction. Monitoring
freeze suppresses configuration/action mutations, not observations; explicit maintenance suppresses notifications
and records why. Maintenance never changes a stale/unknown observation into healthy.

Create incident transition, audit and notification intent in one DB transaction. Notification workers claim with
fencing, send outside transactions, retry bounded at-least-once with the incident ID as stable correlation key,
and acknowledge under the claim token. An ambiguous provider response can duplicate delivery, never duplicate
an incident transition. Notification destinations are organization-controlled verified channels, secret settings
encrypted, no destination taken from an event. Fake/local recipients only in acceptance. Retry 1–300 seconds for
72 hours then mark delivery failed visibly; monitor outbox age and failure independently. No remediation or
infrastructure authority is included in any integration credential or first-milestone route.

## Implementation and rollout gates

OPS-002 implements inventory tables, strict ancestor foreign keys/uniqueness/version checks, memory and PG store
contracts, app-role grants, API/RBAC and audit/freeze tests. OPS-003 adds credential tables/digest handling and
rotation/revocation concurrency tests. OPS-004 adds event/counter tables, durable commit tests and retention load
scenarios. Apply owner migrations then app grants; least-privilege app roles never get DDL or audit-update rights.
Keep store callbacks retry-safe with no network work inside. Test audit rollback on every management mutation.

Roll out disabled by default to a test organization with local adapters. Activate inventory before credentials,
then ingestion before health/rules. Preserve Business Admin licensing and Rokela PDF's shared subscription.
Production credentials, verified alert destinations, external monitoring and retention/recovery exercises are
later gates, not prerequisites for local contract tests. Roll back by disabling new routes/workers and revoking
integration credentials; keep evidence/tables for inspection, never undo licensing state or drop data as rollback.

OPS-001 tests validate planned schema examples and rejection cases only. They do not prove HTTP authentication,
transaction commit behavior, DB grants, actual credential secrecy, delivery, probes or isolation at runtime. The
live OpenAPI drift test remains authoritative for implemented endpoints. Subsequent tasks must add their full
negative/mutation/PG/load evidence before claiming those controls exist.

## OPS-002 implementation notes

Inventory is a backend API behind an explicit rollout flag; see the
[rollout guide](../deploy/operations-inventory.md). `operations_accounts` is a
per-organization lock anchor, serializing all descendant inventory mutations and
same-org graph/cap checks. This is a coarser implementation of organization-first
locking. Transaction-bound authority checks use the same connection, avoiding
pool exhaustion under lock contention. Future tasks must share this anchor before
locking descendant credentials/counters/events. Inventory is not routed through
best-effort telemetry and grants no collection, licensing or remediation authority.

## OPS-003 implementation notes

Credential management uses `OPERATIONS_CREDENTIALS_ENABLED`, default false, with
inventory/MFA configuration prerequisites. Four management operations are live
contracts; the event ingestion route remains planned. See the
[credential rollout guide](../deploy/operations-credentials.md).

Metadata excludes the verification digest and internal rotation marker. Digests
and identity are immutable; expiry only shortens and revoke/rotation markers
cannot be cleared. An active rotated predecessor prevents another rotation until
expired/revoked. Two independent active credentials can use zero-overlap
replacement without exceeding the cap; a positive overlap requires a free slot.

Fresh MFA consumption precedes the organization lock; management rechecks role,
active session, scope and lifecycle within its own transaction/connection.
`withCredential` supplies the guarded transaction for future ingestion, not a
cacheable authentication result. Verification checks current state, expected
purpose/source/scope, and expiry/enablement before callback and commit. It never
consults commercial subscription state. No HTTP verification/ingestion endpoint
has been added by OPS-003.
