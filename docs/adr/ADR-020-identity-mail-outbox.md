# ADR-020: Encrypted recovery-mail outbox

Reset/verification token hashes, encrypted email and request audit commit in one authentication transaction. Enable durable mode with a separate stable `MAIL_OUTBOX_ENCRYPTION_KEY` (random 32-byte hex), in addition to the existing delivery configuration. Existing direct delivery remains compatible when the key is absent and does not gain durable guarantees. Production rollout requires migration 0010 and app grants before enabling the key.

AES-256-GCM protects the recipient, recovery token and message text. Associated data binds user, purpose, token hash and created/expiry timestamps. The key is separate from MFA and license signing; no plaintext queue or public queue route exists. The queue retains at most one message per user/purpose and removes ciphertext after delivery, expiry, invalidation, tampering or exhausted retries.

Workers lock user before message, recheck authoritative token and user status, and commit a random fenced 60-second lease before contacting the provider. Network sends are outside retryable transactions. Delivery uses the original token digest as the stable provider idempotency key. Crashes after acceptance may replay the send: this is at-least-once delivery subject to provider deduplication, not guaranteed exactly-once delivery or inbox arrival. Six attempts, bounded exponential retry delays and the original 15-minute token expiry limit delivery; retries never extend recovery validity.

An old worker cannot acknowledge a newer lease/message. Multiple workers serialize claims through database state. New token requests may invalidate an in-flight older email; redemption remains authoritative, so that older link fails. Disabled users, consumed/superseded tokens and expired messages are discarded before a new send. Request responses remain generic and do not await the provider. Audit/metrics contain outcomes and purpose, never recipient, token, ciphertext or provider bodies. Cipher/key failures do not silently fall back to plaintext.

An independent five-second worker resumes pending work after restart, regardless of the configurable retention-maintenance interval. Graceful shutdown stops new claims and waits for in-flight delivery. Key rotation requires draining/discarding pending mail before changing the key; lost/changed keys do not decrypt old messages. A failed/expired recovery message can be replaced by a new request after the existing cooldown. Live Resend/domain acceptance remains an external configuration step.
